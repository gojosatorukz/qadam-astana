# Qadam: публикация и постоянный адрес

Каноническое публичное демо: **[qadam-astana-walk.pubg-bekzat.chatgpt.site](https://qadam-astana-walk.pubg-bekzat.chatgpt.site)**.

Публичный репозиторий: **[gojosatorukz/qadam-astana](https://github.com/gojosatorukz/qadam-astana)**.

## Что размещено

Приложение развёрнуто через Sites на Cloudflare Workers. Сборка Vinext/Vite включает React-интерфейс и серверные обработчики:

- `GET /api/places` — публичный снимок POI и метаданные;
- `GET /api/plan` — состояние конфигурации без ключей;
- `POST /api/plan` — retrieval, ограничения, пешеходный граф и серверный вызов Gemini, когда он настроен.

GitHub — источник кода, данных, скрипта сбора и тестов. **GitHub Pages не запускает эти серверные маршруты.** Включение Pages вместо текущего хостинга не является переносом работающего приложения; перенос потребует совместимого серверного runtime. Нельзя решать это вставкой `GEMINI_API_KEY` в браузерный код.

## Не менять идентичность опубликованного проекта

Сохранить `project_id` из [.openai/hosting.json](../.openai/hosting.json), существующий slug `qadam-astana-walk` и указанный канонический URL. Для обновления загружать новую версию **того же проекта**, а не создавать новый сайт или новый slug.

Публичная аудитория уже выбрана для этого демо. Обновление исходников не должно случайно менять её на приватную или переносить проект. Локальная Sites-связь и GitHub-репозиторий независимы: не перенастраивать origin рабочего Sites checkout ради публикации кода в GitHub.

## Подготовка новой версии

1. Проверить изменения, источники данных и отсутствие реальных ключей. В репозитории допустим только пустой [.env.example](../.env.example). Исключить `.env.local`, `node_modules`, `.sites-runtime`, `.wrangler`, `dist`, журналы и локальные выходные файлы.
2. Установить зависимости из `package-lock.json` командой `npm ci`, если окружение ещё не подготовлено.
3. Выполнить проверки:

   ```sh
   npx tsc --noEmit --incremental false
   node --experimental-strip-types --test tests/planner.test.ts tests/extended.test.ts
   npm run build
   ```

4. Передавать `GEMINI_API_KEY` только в серверное окружение/секреты хостинга. Не использовать публичные `VITE_*` или `NEXT_PUBLIC_*` переменные для ключа, не помещать его в клиентские assets, README, demo-запросы или GitHub Actions logs. Модель задаётся `GEMINI_MODEL`; отсутствие ключа оставляет честный `retrieval`.
5. Подготовить и загрузить сборку как новую версию существующего Sites-проекта, затем развернуть эту версию с сохранением публичной аудитории и постоянного URL. Этот протокол не создаёт отдельный новый сайт для каждой итерации.
6. Открыть **тот же канонический URL** в сессии без входа и проверить интерфейс и API. Публикация успешна только после проверки работающего результата.

## Проверка после публикации

- Главная страница доступна публично, карта и данные загружаются.
- `GET /api/plan` не раскрывает ключ; счётчики соответствуют снимку: 890 POI, 81 383 узла, 97 427 рёбер.
- Набережная → кофе → 45 минут → только известные часы → «Сейчас»: непустой план по доступному расписанию. На проверенном снимке Coffee Original (`24/7`), 39 минут с возвратом; при 20 минутах — честный пустой результат.
- Дневной сценарий явно подписан будущей датой. «Завтра, 12:00» не выдаётся за открытие сейчас.
- Если показан Gemini, trace подтверждает успешную генерацию и валидацию ID. При 503 или ошибке grounding интерфейс сохраняет маршрут и обозначает `retrieval`.
- Открыть источник POI и проверить неизвестные часы, маршрут обратно и предупреждение о приближениях.

Подробные фактические выходы и ограничения: [EVALUATION.md](./EVALUATION.md). Прохождение локальных тестов не подтверждает само по себе доступность опубликованного URL или облачной модели.
